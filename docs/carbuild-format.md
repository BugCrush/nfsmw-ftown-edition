# Car model file formats (what our car builder knows)

What `tools/carbuild/` has established about NFS Most Wanted's car files, `CARS\<NAME>\GEOMETRY.BIN` (the model) and
`CARS\<NAME>\TEXTURES.BIN` (its textures). Every statement here is backed by a test in `tools/carbuild/tests/` or a
byte-level observation named beside it; unknowns are listed as unknowns. Spec:
`docs/superpowers/specs/2026-11-01-own-car-build-design.md`; plan `docs/superpowers/plans/2026-11-01-car-builder-part1.md`.

## Chunks (`tools/carbuild/chunks.py`)

- Every file is a list of chunks: `u32 id, u32 size, size bytes`. An id with the top bit (0x80000000) is a container
  whose bytes are more chunks; others are leaves. Id 0 is padding and is kept byte for byte.
- **All 195 car files** in the game (97 `GEOMETRY.BIN`, 97 per-car `TEXTURES.BIN`, the shared `CARS\TEXTURES.BIN`)
  read and write back byte-identical at chunk level (`test_roundtrip_all_cars_chunk_level`).
- Example, GTI `GEOMETRY.BIN` (5,536,128 bytes): `0x80134000` (5,450,664 bytes), then id 0 (85,432), then id 0 (8).
  The container's first child is an empty id-0 chunk (8 bytes of zeros), then `0x80134001`.
- **The Raptor add-on's solid list has a wrong size field**: `0x80134000` says 32,241,444 bytes, but its last solid
  (at 0x1E53780, 444,480 bytes) runs 2,204 bytes past that, and an id-0 chunk of 48 bytes ends the file. Read
  against the file's end, everything nests exactly. The reader keeps such a container's stored size (`Chunk.size`)
  and gives it the children that really belong to it; the game loads the car regardless (it is installed and driven).
- A container whose bytes do not split into chunks is kept as raw bytes (`children` None).

## JDLZ (`tools/carbuild/jdlz.py`)

- Header 16 bytes: `"JDLZ"`, `02 10 00 00`, u32 uncompressed size, u32 compressed size (whole blob with header).
- Two flag bytes, each read when its shifted value has dropped to 1: flags1 bit = literal (0) or back-reference (1);
  for a back-reference, flags2 bit 1 = short form (distance `(b0 & 0x0F) + 1`, length `(b1 | (b0 & 0xF0) << 4) + 3`),
  0 = long form (distance `(b1 | (b0 & 0xE0) << 3) + 17`, length `(b0 & 0x1F) + 3`). flags2 shifts only on
  back-references. Verified: the Longnose Cab's body block (file offset 0x2E00) gives 101,728 bytes starting with
  `0x80134010` (`test_decompress_truck_body`).
- `compress_literal`: flags1 = 0 before every 8 literals, flags2 = 0 once after the first flags1 (read, never used).
  Valid, no size gain (`test_literal_compress_roundtrip`).

## Name hash

bStringHash: `h = 0xFFFFFFFF; h = h * 33 + c` per byte (`chunks.bstringhash`). LONGNOSECAB_SKIN2 = 0x70F85C30,
GTI_CV = 0x5EBDB6FB.

## GEOMETRY.BIN layout (`tools/carbuild/geometry.py`)

**All 92 packs made by the game's own tools round-trip byte-identical** through `read_geometry` / `write_geometry`,
with every header field, offset and padding regenerated by the rules below (`test_roundtrip_geometry_identical`).
Packs made by other tools (the Raptor, the Chiron, the three compressed add-ons) read into the same structure and
are written back in the game's layout with the same content (`test_uncompressed_addons_content_roundtrip`,
`test_compressed_rewritten_uncompressed_reads_back`).

```
0x80134000 solid list
  0x00000000 size 0
  0x80134001 header
    0x134002 info, 144 bytes
    0x134003 index: (name hash, 0) per solid, sorted by hash
    0x134004 directory: (name hash, file offset of the solid's chunk, chunk size incl. its 8-byte header,
             the same size again, flags 0, 0) per solid, sorted by hash
    0x80134008 empty container
  0x00000000 padding: the next solid starts at a multiple of 128 in the file
  0x80134010 solid, padding, solid, ... (no padding after the last solid inside the list)
then the top-level chunks after the list (game packs: usually a large id-0 chunk and a small one; kept as read)
```

- **Padding chunk rule**: gap = bytes to the next multiple of 128; none if 0; an id-0 chunk of gap - 8 bytes if the
  gap is 8 or more, else gap + 120 (proven by the identical round trips; the list's first child is the size-0 case).
- **Info (0x134002)**: +0x08 u32 0x1D (all packs), +0x0C u32 solid count, +0x10 file name ("GEOMETRY.BIN"; the
  add-on tool writes its credit there), +0x48 pack name ("DEFAULT"; "TOOLKIT"), +0x68 u32 **file length** in the
  game's packs (0 in add-on packs), +0x70 u32 0x80 (the alignment, presumably). The writer sets the count and the
  length; the rest is kept.
- **Order**: solids are stored in their own order (not by hash); only the index and directory are sorted by hash.
- **Compressed packs** (CHALLENGER71, FLIPCAR, LONGNOSECAB, made by NFS-CarToolkit): the list's bytes are the header
  then JDLZ blocks, each holding one solid chunk, at the directory's file offsets (flags 0x100, compressed and
  uncompressed sizes), separated by id-0 padding to 128. Directory size = the blob length.
- **The Chiron add-on** keeps only the header in the list; a `0x80134008` and then its solids (each behind id-0
  padding) follow at the top level. Its directory sizes run to the next solid (padding included). The game loads it.
- **The Raptor add-on**: besides the short list size (above), its solids carry a donor car's names in their headers
  (e.g. "CTS_KIT01_BODY_E") while the header's hash (+0x10) is the Raptor's own: **the game goes by the hash**.
  Its alignment runs are zeros instead of 0x11.

### A solid (0x80134010)

- Children in this order: 0x134011 header, 0x134012 texture hashes, 0x134013 shader hashes (missing in one game
  solid), optionally 0x13401A, the mesh container 0x80134100, optionally 0x134017, 0x134018, 0x134019.
- **0x134011 header**: +0x10 u32 name hash (bStringHash of the name; the game's key), +0x20 bounding box (min x, y,
  z, pad, max x, y, z, pad), +0x40 a 4x4 matrix (identity-like), +0xA0 the name, zero-terminated and padded to a
  multiple of 4. Other fields not decoded yet (+0x0C, +0x14, +0x18, +0x88, +0x98).
- 0x134012 / 0x134013: 8 bytes per entry, a hash and 0.
- **Mesh container 0x80134100**: 0x134900 mesh header (48 bytes), 0x134B02 mesh entries (104 bytes each), 0x134B03
  indices, 0x134B01 vertices (one buffer for all of the solid's meshes), then one 0x134C02 per mesh with the mesh's
  name (zero-terminated, padded to 4; e.g. "BODY_DULL_PLASTIC"). One game solid has no 0x134B01. The add-on packs
  have no 0x134C02.
- **Alignment runs**: 0x13401A, 0x134900, 0x134B02 and 0x134B03 data start at a multiple of 16 in the file, 0x134B01
  data at a multiple of 128, after a run of 0x11 bytes (zeros in the Raptor). Solids start at multiples of 128, so
  positions are measured from the solid's start (also in compressed blocks, which decompress to offset 0).
- 0x13401A, 0x134017/18/19: not decoded (kept as bytes).
- **The bounding box** (header +0x20) is the vertex extents **plus 0.01 m on every side** in every game pack and the
  compressed add-ons (GTI, SEMI, Longnose Cab, Challenger: all solids); the Raptor's tool stores the tight extents
  (`test_bbox_is_extents_plus_one_cm`). The truck's "tyre y -0.017..+0.444" was this box; its vertices span
  -0.0066..+0.4340. Our writer must add the 0.01.

### Meshes and vertices (`Solid.meshes()`, `positions`, `normals`, `colors`, `uvs`, `triangles`)

- **One vertex layout everywhere: 36 bytes** = position (3 floats) at +0, normal (3 floats) at +12, colour (D3DCOLOR,
  bytes B G R A; 0xFFFFFFFF in two thirds of the samples) at +24, texture coordinate (2 floats) at +28. Evidence:
  vertex bytes / sum of vertex counts = 36 for all 14,975 solids with vertices (game and add-ons); all positions lie in
  their solid's box (1 mm), normals are unit length (all but 1 of 123,447 sampled, test < 0.1%), whatever the mesh
  flags (`test_vertex_counts_match_chunks_every_car`, `test_positions_inside_header_bbox`, `test_normals_unit_length`).
- **Mesh entry, 104 bytes** (all 41,149 meshes): +0x00 bbox (6 floats: min xyz, max xyz), +0x18..+0x1C five texture
  slot indices into the solid's texture list (slot roles not yet known; slot 0 = `texture_index`), **+0x1D shader
  index** into the solid's shader list (checked: meshes named WINDOW_FRONT use WINDSHIELD, TIRE ones RUBBER, LICENSE
  LICENSEPLATE, DECALn DECAL), +0x1E..+0x2F zero, +0x30 u32 4 (0 in 22 meshes), +0x38 u32 flags, **+0x3C vertex
  count, +0x40 triangle count, +0x44 index offset (in indices), +0x5C index count** (= 3 x triangles everywhere:
  **triangle lists**, not strips), everything else zero.
- **Vertex ranges**: mesh k's vertices follow mesh k-1's (offset = sum of earlier vertex counts); indices are 16-bit
  and count from the solid's first vertex, so a mesh's indices lie in [offset, offset + count). One exception: the
  Challenger's `CHALLENGER71_STYLE13_HOOD_A` mesh 3 uses vertices of other meshes (still inside the solid's buffer).
- **Flags** seen: 0x4080, 0x4180, 0xC000, 0xC080, 0xC180, 0x14080, 0x14180, 0x1C180, 0xA24180 (damage meshes), 0xA34180;
  every one with the 36-byte layout, so they are not a vertex format switch. Meaning not decoded.
- **Mesh header 0x134900** (48 bytes): +0x08 u32 18, +0x0C u32 the OR of the meshes' flags (all but 74 solids), +0x10
  mesh count, +0x18 u32 1, +0x2C total index count; other fields zero. The indices chunk is padded with two zero bytes
  to a multiple of 4 when the count is odd (4,572 solids; 16 add-on solids are not).
- **UVs**: 389 of 41,149 meshes in the game's own cars carry tiling coordinates beyond +-8 (grilles, window masks; up to
  83,745 on the Punto's window mask), so a UV range check can only be statistical (`test_uvs_in_reasonable_range`).

## TEXTURES.BIN (`tools/carbuild/textures.py`)

**All 89 texture packs in the game's layout round-trip byte-identical** (`test_roundtrip_textures_identical`: every
non-empty per-car pack except the Raptor's and the Chiron's, plus the shared `CARS\TEXTURES.BIN`); 7 car folders
have an empty TEXTURES.BIN. **There is no uncompressed pack in the game**: every texture is its own block.

```
0xB3300000 pack
  0x00000000 padding to 64 (48 bytes)
  0xB3310000 info
    0x33310001 124 bytes: u32 5, pack name (28 bytes, "CARTEXTURES"), file name (64 bytes,
               "Global\Pipeline\CarTemplateTextures_GTI.tpk"), +0x60 u32 a hash (repeated in 0x33320001)
    0x33310002 (texture hash, 0) per texture, sorted by hash
    0x33310003 (texture hash, file offset of the block, stored size, decoded size, 0x100, 0), sorted by hash
  0x00000000 padding to 128
  0xB3320000 data
    0x33320001 24 bytes: 0, 0, 1, the info's hash, 0, 0
    0x00000000 padding to 128 (Binarius-written packs carry "Binary by MaxHwoy | Automated" in it)
    0x33320002 120 bytes of 0x11, then the blocks (file order is not hash order), each starting at a multiple of 64;
               the chunk ends at the next multiple of 64 after the last block
```

- **Blocks**: 1,144 `JDLZ` (header csize = stored size), 87 `HUFF` (EA Huffman, `30 FB` stream; header csize + 16 =
  stored size; 3 textures in each of 29 cars; **not decoded**: kept as stored, so they round-trip but have no
  pixels or names here), 16 `RAWW` (stored as is: `"RAWW" 01 10 00 00`, size, size + 16; written by the Raptor's
  tool, so the game reads uncompressed blocks: our writer's `compressed=False` form). The bytes between blocks are
  sometimes left-over compressor output, not zeros: kept with the texture while it is unchanged.
- **A decoded block** = pixel data (all mip levels, largest first) + 156 bytes: the game's TextureInfo (124 bytes) and
  32 more. Fields checked over all 1,160 decoded textures: +0x0C name (24 bytes, cut to 23 characters, so long names
  do not hash to the key), +0x24 name hash (= directory hash, all), +0x28 class hash, +0x30 image placement, +0x34
  palette placement, +0x38 image size, +0x3C palette size, +0x40 base image size, +0x44 u16 width, +0x46 u16 height,
  +0x48/+0x49 log2 width/height, +0x4A compression (0x22 DXT1, 0x24 DXT3, 0x26 DXT5, 0x20 uncompressed A8R8G8B8),
  +0x4E mip levels; in the 32 bytes after: +0x88 u32 5, +0x8C u32 6, **+0x90 FourCC** ("DXT1"/"DXT3"/"DXT5", or D3D
  format 21 = A8R8G8B8). Data length = the mip chain's size for every game texture (`test_compressed_pack_reads`).
  Formats in the game: DXT3 650, DXT1 341, A8R8G8B8 150, DXT5 1.
- **Tool packs**: the Raptor's aligns blocks to 128 and stores whole mip chains while the headers say one level (and
  RAPTOR_SKIN2 is 896 x 1024, not a power of two); the Chiron's has no data container (blocks straight after the
  info, unaligned) and also stores whole chains under a one-level header. Both read, and are rewritten in the game's
  layout with the same content (`test_tool_layout_packs_content_roundtrip`).
- **Texture slots** (mesh entry +0x18..+0x1C): slot 0 is the diffuse texture, slot 1 the normal map where there is one
  (GTI badging: GTI_BADGING, GTI_BADGING_N, GTI_BADGING x3); other slots repeat slot 0. Many slot textures (paint,
  windows, grilles) are not in the car's own pack or the shared one: they come from global packs or are swapped at
  run time.
- `to_dds` writes a DDS (FourCC DXT1/3/5, or 32-bit BGRA masks for A8R8G8B8) with all mip levels.

## Logos in the car select (`tools/carbuild/logo.py`, `tests/test_logo.py`)

Front-end textures in `FRONTEND\FrontB.lzc` (packs FRONTENDTEXTURES and FRONTENDTEXTURESPC), looked up by name hash:

- **Maker logo: `CARSELECT_MANUFACTURER_<maker>`** (`FECarRecord::GetManuLogoHash` 0x591330: `sprintf
  "CARSELECT_MANUFACTURER_%s"`, then 0x503400 checks the texture exists, else `GENERIC_LOGO_128`). With the Unlimiter's
  manufacturer hook (`EnableManufacturerHook = 1`, ours) the maker is the name of the car's `frontend` entry's parent
  node (`bugatti`, `mahindra`).
- **Model logo: `SECONDARY_LOGO_<frontend CollectionName>`** (`GetLogoHash` 0x591240, else `GENERIC_LOGO_256`); the
  Unlimiter's `SecondaryLogoFix = 1` (ours) shows it even for a maker the game doesn't know.
- Both names are hashed by 0x5AF1C0, **bStringHash with a..z upper-cased**, so lower-case node names work. The pack
  stores names cut to 23 characters (`CARSELECT_MANUFACTURER_` is exactly 23: every maker logo's stored name is that
  prefix alone); the lookup is by the full name's hash.
- Sizes and formats: every maker logo in the game is **128 x 64 DXT3** (26 of them, one mip level), the Chiron's 128 x 64
  DXT3 with 8 levels; model logos are 256 x 64 DXT3 in the game, the Chiron's 512 x 128 DXT3 (10 levels), the Flip Car's
  1024 x 256. The Chiron's maker logo is coloured (Bugatti's red oval), its model logo a white wordmark.
- The Thar's (`logo.py`, as the Chiron's): `CARSELECT_MANUFACTURER_MAHINDRA.dds` (128 x 64, Mahindra's 2021 SUV "Twin
  Peaks" logo from Wikimedia Commons, its own silver colours) and `SECONDARY_LOGO_THAR.dds` (512 x 128, "THAR" in white
  Arial Bold), DXT3 with full mip chains (our own encoder: explicit alpha; end colours from the block's visible pixels,
  since the download's edges carry nearly transparent pixels of any colour that otherwise tinted blocks yellow and red).
  Neither hash exists in the game's front end yet. Bound by Binarius `bind_textures synchronize ... FRONTENDTEXTURES
  <folder>` (the Chiron package's line), which names each texture after its file.

## Parts list, car type and collision of a new car (`tools/cars/packages/thar/`, `tools/carbuild/donor.py`)

- **Parts list** (`DBModelParts.bin`, Binary's serialized form: `gMpB`, size (len - 8), 2, a hash, size (len - 20),
  `RAWW`, 0x1001, size (len - 36), size (len - 20), then records with null-terminated strings): nothing in it depends
  on the strings' lengths except the four size fields, so a template is renamed by substitution and the sizes
  rewritten (`make_parts.py`; the Longnose Cab / Tomahawk template, LONGNOSECAB -> THAR, GTI(_0n)_CV -> THAR(_0n)_CV).
- **Car type** (`CarTypeInfos.bin`, same header): the record as the CarTypeName and ManufacturerName strings, then the
  remaining fields of the game's 0xD0-byte CarTypeInfo without the derived ones (BaseModelName, GeometryFilename,
  CarTypeNameHash, pad0, Padding): ... Type, **UsageType (the int just before CarMemTypeHash = bStringHash("Racing")
  0x79602673 for racers)**, MaxInstances[5], WantToKeepLoaded[5], MinTimeBetweenUses[5], AvailableSkinNumbers,
  DefaultSkinNumber, **Skinnable (the byte before the last four)**, DefaultBasePaint (the last four). The Tomahawk's,
  the Chiron's and the Longnose Cab's records are the same bytes apart from the names, Skinnable (the truck's 0) and
  DefaultBasePaint. The Thar's is the Tomahawk's with THAR / MAHINDRA (`make_cartype.py`).
- **Collision**: the database names one model (`MODEL` holds one name in Attribulator), so a car without its own
  collision gets a game car's copied under its name (`copy_collection GLOBAL\GLOBALB.LZC Collisions <DONOR> <CAR>`).
  `donor.py` measures the bodies (union of `<CAR>_KIT00_BODY_A` and `<CAR>_BASE_A`, by hash, in the model's frame,
  where the collision lives) of the 37 stock racers and picks the smallest worst relative difference over length,
  width and height. The Thar's body is 3.99 x 1.94 x 1.39 m in its frame (the 1.78 m of the spec is its height above
  the road, with its 40 cm ride height and wheels below the body); the closest racer is the **Golf GTI** (4.22 x
  1.76 x 1.29: +5.7%, -9.0%, -7.4%), then the TT (9.7%), A3 (10.0%), Impreza (11.2%), Clio and Punto (11.8%).

## Building parts that did not come from a game file (`geometry.finalize`, `check`, `extents_bbox`)

`finalize(solid)` fills in what the game's tools compute: the mesh header's flags OR (+0x0C), mesh count (+0x10) and
index total (+0x2C), the indices' zero padding to 4 bytes, and the box (vertex extents + 0.01 m; a box already within
0.1 mm is kept, since the game's tools round in single precision). `check(solid)` lists disagreements (empty for every
GTI solid). `Mesh.to_raw` refuses an entry that isn't 104 bytes or a slot list that isn't 5 long, and writes
`texture_index` as slot 0. Textures: a re-encoded texture gets its new decoded size in the directory, and a pack whose
file name changes gets its key (info +0x60 and 0x33320001) recomputed as bStringHash(file name), which is what every
game pack holds (the Raptor's tool writes 0). A texture pack still needs a donor's info bytes (`raw_parts["info"]`).

## Axes (from the parts' boxes, confirmed by the renders)

**+X forward, +Y left, +Z up**, metres, origin on the ground-ish centre of the car: headlights at +X (GTI
LEFT_HEADLIGHT x 1.57..2.00), brake lights at -X, LEFT_ parts at +Y; the body's lowest point is near z 0 (GTI -0.02).
GTI body 4.24 m long, 1.78 m wide, 1.27 m high.

## Origin and wheels (`tools/carbuild/conventions.py`, `tests/test_conventions.py`)

Measured on 17 racers (GTI, BMWM3GTR, CORVETTE, MUSTANGGT, RX8, GALLARDO, CAMARO, VIPER, SUPRA, CLK500, ELISE, CTS,
FORDGT, SLR, 911TURBO, PUNTO, A3) against their `ecar` TireOffsets / TireSkidWidth and `chassis` RIDE_HEIGHT (database
unpacked by Attribulator, cached under `.superpowers/carbuild/cache/`), plus the game's code where noted:

- **The tyre model** (`<CAR>_KIT00_FRONT_TIRE_A`, rim and tyre in one solid; no racer has a REAR_TIRE solid) is centred
  on its axle in x and z, and in y **starts at its outer-face plane (y within 4 cm of 0) and extends to +y** by its
  width (GTI -0.005..+0.237). `TYRE_SIDE = +1`.
- **How the game draws it** (speed.exe): `0x755C4A` takes the tyre model's box (extents + 0.01 m a side): width = box
  y size, radius = box x size / 2; each wheel is scaled by TireSkidWidth / width across and W / radius in size (so rear
  wheels with a larger W use the front model enlarged: Viper +6.5%). `0x74F054..0x74F235`, per wheel, with
  s = TireSkidWidth / 2: a matrix scaling y by k = skid / width and shifting by -s, then a translation by Y + s for a
  right wheel (Y < 0) or Y - s for a left one (constant 0.5 at 0x903314). Result: right y = Y + k*y_m, left
  y = Y - skid + k*y_m, so both tyres cover |y| in [|Y| - skid, |Y|] (to the box margin: the GTI's right tyre sits
  2.6 cm further out than its left). **|TireOffsets Y| is the outer face.** The left tyres (FL, RL) are also turned
  half a turn about z after the scale and shift (so left y = Y - k*y_m, not the formula above; LeftTireRotateZMatrix
  0x9B3600, picked at 0x74F462; a mirror 0x9B0BF0 if mMirrorLeftWheels), so the model's y-min face looks outward on
  both sides and its y-max face inward. Every racer's tyre closes that
  inner face with a 2-triangle PLAINNOTHING square (global texture 0xE38806E3, flags 0x4080); the Thar's has one too.
- On every racer **the body's side at the wheel lies 0..6 cm outside |Y|** (widest |y| of body vertices within the
  wheel's length and below its top).
- **Origin height (`ORIGIN_Z = "body_min"`)**: the body's lowest point is at z = 0 (-0.08..+0.02 on every racer).
- **Where the game draws the wheel centres** (`conventions.race_wheel_centre_z`, `fe_wheel_centre_z`; speed.exe and the
  nfsmw decompilation, `docs/cars-notes.md` "Thar fixes 2"): car select **z = Z + FECompressions[axle]** (0x737AD0);
  races **z = Z + W - RIDE_HEIGHT*0.0254 + c - ecar RideHeight*0.0254** (RIDE_HEIGHT, TRAVEL and ecar RideHeight in
  inches; c the spring's compression, at rest k c (1 + progression c) = the wheel's load, k in lb/in), then lowered
  by however far the highest tyre top (z + W) rises above ecar WheelWell (inches; racers inherit 22.5; 0 = off;
  0x74736D..0x747425). The two agree within a median 1.3 cm on 25 racers. Body offset and clamp apply only to cars
  near the camera. The physics holds the collision's root box bottom RIDE_HEIGHT - c above the
  road, so the drawn wheels touch the road when that bottom is at z = Z (every racer's: pivot y = half height).
  Part 2's z = W - RIDE_HEIGHT/100 (RIDE_HEIGHT read as cm) was a fit to fender gaps, not the game's rule.
- **Origin along the car (`ORIGIN_X = "body_centre"`)**: the middle of the body's length (within 0.2 m; the axles'
  midpoint is up to 0.25 m off). Front axle X > 0 > rear axle X.
- **A model without a chassis** (the Thar: its lowest point is its bumpers, above the wheel centres): the rule at a
  ride height inside the suspension's travel fixes where the wheel centres sit against the origin, so the preparation
  moves the model by `origin_z_offset` (`blender_prep.py`, config `ride_height_cm`) and the body's lowest point ends up
  above the origin (the Thar: +0.307 m at RIDE_HEIGHT 9.3). RIDE_HEIGHT 40, which the rule wanted with the body's
  lowest point at the origin, made the body float above wheels hanging at full droop in races (first test-copy race).
- **Traffic is different**: the SEMI's tyre is centred on its hub plane (-0.229..+0.247), TAXI and the TRAF* cars
  similar. The rule above is the racers'; the Thar follows it.
- **The Longnose Cab breaks the rule**: its TireOffsets |Y| (1.35 front, 1.25 rear) lie 3-5 cm outside its body at the
  wheels, the placement above puts its right tyres another 2.4 cm (front) and 4 cm (rear) further out than the left
  ones (its tyre model spans -0.007..+0.434 in a box 0.46 wide, squashed to 0.325 / stretched to 0.555), and its body
  reaches z -0.18, 11 cm below the road at RIDE_HEIGHT 7: the floating right-front wheel and the sparks under the
  chassis.

## The preparation folder (`tools/carbuild/blender_prep.py`, `carbin.py prep`)

Objects hidden from renders, objects whose collections are all hidden from renders or excluded from the view layer
(boolean cutters, e.g. the Thar's `Cube.001` in "extra"), empty objects and the config's `drop` list are left out.
Between Blender and the assembler: `parts.json` (format `carbuild-prep`, version 1: `scale`, `source_box`,
`source_box_without_wheels`, `origin_shift`, `dropped`, and per part (game name without the car prefix, e.g.
`KIT00_BODY`) its `materials` (source material names; an empty slot takes the config's `material_for_unassigned`),
source `objects`, and per detail level `file`, `triangles`, `box`, `ratio`), one `<PART>_<LOD>.bin` per part and level
(triangle corners, unindexed: all positions as float32 x 3, then all normals, then all uvs as float32 x 2, then one
uint16 material index per triangle), and `wheel.json` (`radius`, `width`, `side` = conventions.TYRE_SIDE, the four
wheel `centres` and `outer_y`, the |y| of each wheel's outer face, in game coordinates). Each level records `method`:
`collapse` (Blender's Decimate, outermost vertices held) or `drop_smallest` (a tiny part: the previous level less its
smallest triangles), and every level's box is within 1.5 cm of level A's. The tyre part is the
front-right wheel, centred in x and z, outer face at y = 0, extending to +y.

## Assembling new parts (`tools/carbuild/assemble.py`)

- **Mesh size**: no mesh in the game's own cars has more than 1,000 triangles (39,330 meshes); the most vertices in one
  mesh is 2,910. The assembler splits at 1,000.
- **Solid header counts**: +0x14 u32 = the solid's triangles, +0x19 = texture list length, +0x1A = shader list length
  (912 of 918 solids in GTI, SEMI, CORVETTE, RX8; `test_header_counts_rule_on_game_solids`). +0x18 and +0x1B are 0.
  **+0x98 x +0x9C = the triangle count** on every GTI and Corvette solid (GTI_BASE_A 4.4058 x 326.84 = 1440: an
  area-like figure and a density); the Chiron and Raptor add-ons write (1.0, triangles), the compressed add-ons (0, 0):
  the assembler writes (1.0, triangles) (`test_header_density_fields`). Still undecoded: +0x0C (0x00400016 in the GTI,
  0x00400018 in the Chiron/Raptor), +0x88/+0x8C (0x000EA550 twice); copied from the donor solid of the same part and
  level.
- **Mesh boxes** (entry +0x00) are the mesh's vertex extents +- 0.01 m (all 779 GTI meshes).
- **Position markers, chunk 0x13401A**: 80-byte records: name hash, three zero words, a 4x4 matrix (position in floats
  12..14). GTI: BASE (every level) LEFT/RIGHT_HEADLIGHT, LEFT/RIGHT_BRAKELIGHT, LEFT/RIGHT_REVERSE and three unnamed
  (0x90C81258 at the roof's front, 0xC93B73FD at the centre brake light, 0xF0A9F3CF at the rear centre); KIT00_BODY
  LEFT_EXHAUST (kits 01-04 one or two exhausts each); FRONT_TIRE FRONT_BRAKE and REAR_BRAKE at (0, 0.005, 0).
- **0x134017 / 0x134018 / 0x134019** (on the GTI's skinned and glass parts; 0x134018 is 25,808 bytes on the body) are
  not decoded; the working add-ons (Longnose Cab, Raptor) have none, so the assembler writes none.
- **Lights**: lamp meshes reference the game's generic names HEADLIGHT_LEFT/RIGHT, HEADLIGHT_GLASS_LEFT/RIGHT,
  BRAKELIGHT_LEFT/RIGHT, BRAKELIGHT_GLASS_LEFT/RIGHT (glass slot 4: `<CAR>_KIT00_HEADLIGHT_GLASS_OFF`), which the game
  swaps for `<CAR>_KIT00_HEADLIGHT_OFF/_ON/_DAMAGE0`, `<CAR>_KIT00_HEADLIGHT_GLASS_OFF/_ON/_DAMAGE0` and the brake light
  ones (Unlimiter CarRenderInfo.h; the GTI's pack lacks some of them, e.g. HEADLIGHT_OFF and every DAMAGE0).
- **New textures** (`textures.new_texture`): A8R8G8B8, one level, header from a donor (+0x0C name cut to 23, +0x24 full
  name's hash, +0x30 placement, +0x38/+0x40 sizes, +0x44/+0x46 size, +0x48/+0x49 log2, +0x4A 0x20, +0x4E 1, +0x4F 0,
  +0x90 21). The game's own A8R8G8B8 textures (shared CARS pack, WHEELS) have +0x4F 0 and one level; the Flip Car
  add-on's have +0x4F 3. Glass textures take the GTI's brake light glass header (alpha flags at +0x51..+0x56).
- RUBBER with flags 0x4180 and one texture in every slot: 99 game tyre meshes (no normal map needed).

## A borrowed interior and driver (`tools/carbuild/interior.py`, `assemble.borrow_interior`)

- Every racer has `<CAR>_KIT00_INTERIOR_<A..D>` (shader INTERIOR with its own `<CAR>_INTERIOR` texture at A/B; C/D a
  dark shell, shader PLAINNOTHING, global texture 0x1B049702) and `<CAR>_KIT00_DRIVER_<A, C>` (the same 1,168-triangle
  driver in every car, shader DRIVER, global DRIVER_PLAYER in `GLOBAL\InGameA.bun`; C a 4-triangle DRIVER_CUTOUT in
  GlobalB). Police cars have a driver only, on their skin.
- **The parts list draws them by struct entry**: the INTERIOR part (name hash bStringHash("<CAR>_INTERIOR"), group 28,
  no attributes, struct offset 55) and DRIVER ("<CAR>_DRIVER", group 43, struct 70) are the same records in the GTI,
  the SL500 and the Longnose Cab template, so a car made from the template draws `<CAR>_KIT00_INTERIOR_<LOD>`.
- **A car's own textures are loaded by name** from a fixed list (`<CAR>_SKIN1`, `_MISC(_N)`, `_INTERIOR(_N)`,
  `_BADGING(_N)`, `_DRIVER`, `_ENGINE`, `_LOGO`, `_TIRE(_N)`, `_RIM`, lights...: Unlimiter CarRenderInfo.h
  GetUsedCarTextureInfo; the game's car packs hold only such names), so a borrowed `<DONOR>_INTERIOR` is copied as
  `<CAR>_INTERIOR` and the solids' texture lists renamed; a donor using another own texture (the SL500's `_MISC`) is
  passed over.
- The undecoded 0x134017..19 chunks of the donor's far levels are left out (as for every part we write).
- The Unlimiter's `[Parts] Interior` / `[Visual] Driver` only show and randomise those slots in the customisation menu.

## Renders (`tools/carbuild/blender_view.py`, `carbin.py render`)

Since part 2: `--wheels-at <wheel_report.json>` places the tyre part at the four TireOffsets as the game draws it
(scaled to W / box half length and TireSkidWidth / box width; right tyres at y = Y + y_m; left tyres turned half a turn
about z, which gives the same span [Y - width, Y] as speed.exe's translation and points the rim outward: whether the
game turns or mirrors the left tyre is in the wheel's own matrix, not decoded); `--compare <car config>` also renders
the source .blend from the built car's framing box and writes `compare_sheet.png`; `--masks` adds black-on-white
silhouettes (`mask_*`) for overlap checks (`tests/test_thar_render.py`).


Portable Blender 4.3.2, headless, Workbench engine (studio light, texture colours): front, side (from the right),
rear and front-left three-quarter, 1280x720, each framed so the parts' box fills the frame. Default parts: detail
level A, kit 00, no damage/shop (STYLE)/decal-placeholder parts, no tyres or brakes (the game places wheels from
`ecar`). Slot-0 textures come from the description's texture packs (`--textures` adds e.g. the shared pack); CARSKIN
meshes get a flat paint red, other untextured shaders flat colours. Checked by eye on 2026-11-01 (renders in
`.superpowers/carbuild/renders/`, git-ignored): **GTI, SEMI, Longnose Cab and Challenger each look like their car**:
body, base, glass, mirrors, lights, grille, badges and plates in place; wheel arches empty as expected. Nothing wrong
seen. The Longnose Cab's body and glass are complete; its earlier "broken" look in the game came from the wheels
(`ecar`/tyre), not the body model.

## Description folder (`tools/carbuild/describe.py`, `carbin.py dump|build`)

`car.json` (format `carbuild-geometry-description`, version 1): `info` (hex), `extra` (top-level chunks after the list;
zero-filled ones as `{"zeros": n}`), and per solid: `name`, `name_hash`, `bbox` (6 floats), `header` (hex; the named
fields are written over it on load), `textures` / `shaders` (hash lists), `mesh_header` (hex), `meshes` (per mesh
`bbox`, `texture_slots`, `shader_index`, `flags`, `vertex_count`, `triangle_count`, `index_offset`, `index_count`,
and `raw` hex underneath), `mesh_names`, `other` (undecoded chunks), and the paths of `vertices/<k>_<name>.bin` and
`indices/<k>_<name>.bin`. `obj/<k>_<name>.obj` is a viewing copy (one object per solid, one group per mesh, material
name `tex_<slot-0 texture hash>_shader_<shader hash>`, v flipped to OBJ's convention) and is not read back.
Proven lossless by `test_dump_load_identical` (GTI, SEMI, Raptor) and `test_cli_roundtrip`.

Textures (`textures.json`, format `carbuild-textures-description`): pack name, file name, info and padding bytes, and
per texture its decoded fields, its 156-byte header (hex; authoritative), `textures/<k>_<name>.bin` (pixel data),
`textures/<k>_<name>.dds` (viewing copy, not read back), and `stored/<k>.blk` (the block as stored plus the bytes
after it, with a digest of the data and header it holds: a texture whose data or header changes is re-encoded).
